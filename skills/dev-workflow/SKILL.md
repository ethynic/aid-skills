# 三智能体开发流程

针对非平凡的代码开发任务（新功能、Phase 开发、重构、多文件 bug 修复），按本流程**串行**执行三个独立智能体，把问题拦截在合并前，避免"自己写的自己测"盲区。完整流程在**与用户确认的工作分支**上进行（是否建分支、是否用独立 worktree 都先问用户）：每个 Phase 经开发、测试和 CR 通过后，由 CR 智能体提交并推送；合并回主分支前由用户人工把关。

## 为什么需要这个流程

凡是"合并即上线/部署"的项目，一旦合入的代码有 build 错误或启动错误，服务/应用直接挂掉。本流程通过三个**独立**智能体的串行校验把问题拦在合并前：

- **开发智能体**：写代码 + 单测，自测通过
- **测试智能体**：独立跑测试 + 回归 + 启动安全检查，修明显问题（不复用开发的判断）
- **CodeReview 智能体**：只读评审源码，按严重度报告问题、不修代码；通过后提交该 Phase（不复用前两者判断）

三个智能体**串行执行，后一个等前一个完成才启动**，每个独立验证。

> 本流程提到的 `Agent`、`AskUserQuestion` 等是工具示例名：执行时映射到当前环境实际可用的等价能力（派生子智能体、向用户提问等）；对应能力不存在时不得假装调用成功，向用户说明缺口。

## 何时使用 / 何时简化

| 任务类型 | 流程 |
|---------|------|
| 新功能 / Phase 开发 / 多文件改动 / 触及启动链路 | ✅ 完整三智能体流程（分支与 worktree 均先与用户确认） |
| 单文件 bug 修复（含测试） | 🔧 开发 + 测试两步（CR 可选），在当前工作区做，是否建分支与用户确认 |
| 单行修复 / typo / 纯文档 | ⚡ 直接改，自测即可 |
| 紧急 hotfix | ⚡ 直接改 + 自测 + 用户授权后提交，事后补 CR |

**判断标准**：改动是否触及启动链路（入口文件、调度器、配置加载、依赖清单）或多模块？是 → 完整流程。

## Git 工作区策略

完整流程在与用户确认的工作分支上进行：**每个 Phase 经 CR 通过后提交推送，合并主分支前用户人工把关**。是否建分支、是否用独立 worktree 都先与用户确认，不作为流程默认门槛；未划分多个 Phase 的任务按一个 Phase 处理。

1. **选择工作区与分支**（步骤 0 执行）：
   - 查看当前分支和已有改动。当前已在合适的非主分支时可直接使用；在主分支时**先询问用户**：建功能分支开发，还是直接在主分支修改？由用户决定，默认建议建分支。分支命名遵循项目规范，无规范时用 `dev/<任务简述>`。
   - worktree 同样先询问：并行任务、工作区有其他改动或需要隔离验证时，建议独立 worktree 并说明原因；用户选择不用时，在当前工作区继续，不把 worktree 作为流程门槛。
   - 选用新 worktree 时放在仓库旁，目录名避免含 `/`，并安装其不共享的依赖（如 `node_modules`/`target`）；已有合适的 worktree 则直接使用。
2. **同步主分支**：开发第一个 Phase 前，以及开始后续 Phase 前，把最新主分支同步进当前工作分支（用户选择直接在主分支开发时，拉取最新主分支即可）；开发结束交接测试前再检查一次，有新提交就先合并。有冲突先解决并验证受影响部分，再继续。已有未提交改动时先按实际情况处理，不覆盖或默认 stash。记录合入的主分支 commit 和冲突解决，交接测试与 CR；同步主分支产生的 merge commit 不属于 Phase 提交，绝不因此把工作分支合入主分支。
3. **每个 Phase 的 CR 通过后**：只有 CR 智能体认定本 Phase 的源码审查、相关测试和必要启动检查均通过，才由 CR 智能体只暂存本 Phase 相关文件并 commit 到选定的工作分支；确认远程目标后推送，仓库无 remote 则记录未推送。开发、测试智能体和主控者不提前提交 Phase 成果。CR 提交前用 `git status` 排除无关改动，提交说明遵循项目规范；若项目对分支提交另有限制，以项目规则为准。
4. **主分支**（master/main）：来自功能分支的合并**必须**等用户人工审核代码 + 线下验证通过、明确说"合并"后才执行（见步骤 5）。用户明确选择直接在主分支修改时，CR 通过后的提交即视为已获该选择授权；其他分支可按所用开发流程提交推送。
5. **简化流程**（两步/直接改）不建额外 worktree；若当前在主分支，与完整流程同样先询问用户（建分支还是直接改）。提交遵循项目授权规则。

## 步骤 0：准备（主控者执行）

1. 读取相关设计文档和现有代码，理解需求和既有模式。
2. 若需求不明确或有多种实现方式，用 AskUserQuestion 澄清后再开工。
3. 建立任务 todo list。
4. 探测项目技术栈（决定后续"启动安全检查"用什么命令，见末尾"技术栈命令速查"）。
5. 探测项目是否有自己的**代码评审准则文档**（常见位置：`docs/reviews/`、`.claude/rules/`、`AGENTS.md` 引用的评审规则）。找到则记下路径，供步骤 3 挂载给 CR 智能体——项目准则优先于本技能默认审查重点。
6. 按"Git 工作区策略"与用户确认工作分支与是否使用 worktree，同步最新主分支；使用新 worktree 时装好依赖。向用户报告分支名、工作区路径及选择理由。

## 步骤 1：开发智能体

用 `Agent` 工具（subagent_type: `general-purpose`）启动，prompt **自包含**：

- **选定工作区的绝对路径**（智能体只在该路径内工作，不碰其他工作区）
- 需求背景、要实现什么
- 关键技术事实（已验证的入口点、命名约定、配置位置等，避免智能体重复探索）
- 约束：
  - 遵循既有代码风格（注释语言、命名、错误处理范式）
  - 配置变更要所有相关文件**同步**（如 settings + config 同一字段名一致）
  - **先写测试再实现（可选）**：新功能核心逻辑或 bug 修复适合先用测试明确目标行为时，向用户用通俗语言建议：“先写一个能验证预期行为的测试，确认修改前它因功能缺失或问题存在而失败，改完后再确认通过。”同时说明收益和成本，不只说“Red→Green”或“TDD”。用户可以拒绝；拒绝后按常规方式开发并完成必要验证，不以先写测试作为开工或交付门槛，也不反复征求。无论是否采用，测试都应验证业务意图，不得为了通过而删除、禁用或弱化有效断言。配置、纯样式、文档等任务通常无需建议此流程
  - 测试覆盖核心路径（命中/未命中/异常/边界）
  - 本次新增和受影响测试通过；记录无关的历史或环境失败
  - **不提交、不 push**（本 Phase 在 CR 通过后由 CR 智能体提交）

**报告必须包含**（主控者按此模板验收，并原样转交下一棒）：

```
改动文件：新增 <...>；修改 <...>；删除 <...>
实现要点：<关键设计决策，≤5 条>
测试：位置 <...>；命令 <...>；结果 <X 通过 / Y 失败>；是否先写测试 <是：修改前失败、修改后通过 / 否：原因>
已知风险：<自认不稳的地方 / 未覆盖场景>
```

主控者核验，并在交接测试前检查主分支是否有新提交；有则先合并到当前工作分支、解决冲突并做受影响自测 → 交接给测试智能体；此时不提交 Phase 代码。

## 步骤 2：测试智能体（开发完成且自测通过后启动）

用 `Agent` 工具启动，prompt **自包含**：

- **选定工作区的绝对路径** + 开发智能体的报告（按模板原样转交）
- 要求：
  1. 跑新功能测试
  2. **回归测试**（按影响范围，不无脑全量）：改动文件及其调用方/被调用方所在模块的测试必跑 + 有实际依赖关系的相邻模块；仅当改动触及共享核心（公共库、配置、启动链路）时才跑全量
  3. **启动安全检查**（关键，避免服务挂）—— 按项目技术栈选命令（见末尾速查表），至少覆盖：
     - 语法/编译检查
     - import/依赖加载检查（新增符号能正确导入）
     - 配置加载检查（若触及配置）
     - 前端 build（若有前端改动）
  4. 自己读一遍实现，查明显 bug（拼写错、异常未隔离、参数未参数化等）
  5. 修**明显的**问题（import 错、SQL 错、签名不匹配、断言被弱化），修复最小化、外科手术式；**结构性问题（需改设计/接口/数据结构）不修**，报告主控者
  6. 预先存在/环境问题（缺可选依赖、需真实外部服务的 e2e）记录但不修；说明证据和是否影响本次相关验证，原样告知 CR 智能体
  7. 修复后**重跑**相关测试确认绿
- 约束：**不提交、不 push**
- **报告必须包含**：

```
新功能测试：<命令> → <结果>
回归：<范围> <命令> → <结果>
启动安全：<逐项命令> → <逐项结果>
修复清单：<修了什么、为什么>
未修清单：<问题> <原因>
结论：<本次相关测试及必要启动检查是否通过；历史/环境失败及其影响>
```

主控者核对最终工作区状态的相关测试和必要启动检查证据 → 交接给 CR 智能体；此时不提交。

## 步骤 3：CodeReview 智能体（本次相关验证通过后启动）

**启动条件**：主控者亲自核验测试报告，确认本次新增及受影响测试、必要启动检查通过后启动 CR。已知的无关历史失败或环境失败不阻止审查，但须把失败、依据及影响交给 CR；若它使本次相关验证无法完成，就不能视为通过。测试与 CR 串行，避免验证和审查针对不同代码状态。

用 `Agent` 工具启动，prompt **自包含**：

- **选定工作区的绝对路径** + 改动文件列表（含前两棒报告摘要、主分支同步及冲突解决、历史/环境失败及其影响）

**CR 对源码只读：只报告问题，不修代码。** 修复统一由开发智能体执行，保证评审者独立于实现者。CR 智能体自行判断本 Phase 是否审核通过；仅通过后按“Git 工作区策略”提交该 Phase。

- **审查重点（技术面，按严重度）**：
  1. 正确性 bug（P0/P1）：逻辑错误、SQL 错、属性/字段名错、签名不匹配
  2. 资源/安全：注入（字符串拼值）、连接泄漏、异常未处理致崩溃
  3. 并发/异步：阻塞调用混入异步路径、竞态、循环/资源误用
  4. 启动安全（P0）：import 是否破坏启动链路、循环依赖、懒加载是否正确
  5. 配置一致性：多处配置字段名/默认值是否一致
  6. 测试质量：是否真断言了正确行为，还是 mock 过度变成空测
- **评审纪律**：
  1. **证据链**：每条发现 = 代码位置 + 可发生的触发条件 + 影响 + 最小修正方向；明确区分**已证实缺陷 / 合理风险 / 个人偏好**，不把不可达的假设场景当缺陷
  2. **过度防御也是问题**：重复校验、静默兜底、任意阈值、为不可达场景增加的限制要指出
  3. **范围审查**：实现是否超出设计授权、是否夹带与任务无关的改动
  4. **按影响分级**：命名、格式、可选优化不作为阻断项；P2/nit 只记录
- 要求：
  1. `git status` 核对本 Phase 的范围，检查未暂存和已暂存的 diff、主分支同步时的冲突解决，读未跟踪新文件全文，沿真实调用链核对
  2. 按严重度（P0 > P1 > P2 > nit）输出发现列表
  3. 严格但公平，不编造问题
- 若步骤 0 探测到项目评审准则文档：prompt 附上路径，要求 CR 以项目准则为准绳审查，与本技能默认审查重点冲突时以项目准则优先
- 约束：**审查期间不修改源码；发现 P0/P1、本次相关测试或必要启动检查未通过、证据不足时不提交。已确认无关的历史/环境失败记录在报告中，不单独阻止审核。CR 认定本 Phase 审核通过后才允许暂存、提交、推送本 Phase 的相关文件，不修改源码**
- **报告必须包含**：

```
发现列表：<严重度> <file:line> <触发条件> <影响> <最小修正方向> <已证实缺陷/合理风险/个人偏好>（逐条）
结论：<本 Phase 审核是否通过及依据；若有 P0/P1 单列清单；历史/环境失败的影响>
Phase 提交：<commit hash / 未提交原因>；推送：<目标与结果 / 无 remote>
```

**P0/P1 修复回路**：主控者把 P0/P1 回炉开发智能体修复 + 定向自测 → 测试智能体独立重跑受影响验证 → CR 复核受影响部分确认修复有效并提交该 Phase。P2/nit 记录在案，不阻断本次交付。

## 步骤 4：全部完成——终检与报告（主控者亲自做，不委托智能体）

三个智能体都通过后：

1. 核对 CR 提交的代码状态与交接时的相关测试、必要启动检查证据一致；同一代码状态的有效结果不重复运行。若提交后发现证据失效或遗漏，回到测试与 CR 验证，不能把该 Phase 报告为通过
2. 确认本 Phase 审核通过，所有本 Phase 改动已 commit；有 remote 时确认已推送，无 remote 时记录未推送
3. **向用户报告**：分支名、工作区路径（若用了 worktree 则注明）、commit 列表、三阶段结果摘要
4. **提醒用户**："请人工审核代码并线下验证；确认没问题后告诉我'合并'，我再合并回主分支。" —— 到此停下，不自动合并

---

## 步骤 5：合并回主分支（仅当用户明确确认后执行）

> 用户在步骤 0 明确选择直接在主分支开发的任务无本步骤——成果已由 CR 提交到主分支。

1. `git fetch origin`，确认主分支状态；若主分支有新提交，先把主分支变更 merge 进工作分支（或 rebase 工作分支到主分支）并解决冲突
2. 本地合并到主分支（建议 `--no-ff` 保留分支历史，或按项目习惯），push
3. 清理（默认**不**主动做，用户要求时才做）：仅实际使用了 worktree 时执行 `git worktree remove <路径>`；按需删除工作分支

## 失败与升级路径

1. **修复边界**：测试智能体只修外科手术式问题（CR 不修代码，见步骤 3）。发现需要改设计/接口/数据结构才能解决的结构性问题 → 不修，报告主控者；主控者决定回炉开发智能体重做，或与用户确认方向。
2. **P0/P1 修复回路**：CR 报告问题但不提交，主控者回炉开发智能体修复并定向自测，测试智能体重跑受影响验证，CR 复核后再提交。修复若涉及多文件结构性改动 → 回到测试智能体做一轮独立回归。
3. **避免无效循环**：主控者记录每轮未解决的 P0/P1 及修复结果。相同阻断问题连续两轮修复仍未解决，或连续两轮阻断项没有净减少（包括反复引入同级新问题）时，停止自动回炉，报告现状和可选方向，等用户决定；有明确进展时不因次数机械停止。结构性问题需要重定方案时也先停下说明。

---

## 关键原则

1. **串行不并行**：后一个智能体等前一个完成才启动；本次相关测试与必要启动检查通过后才启动 CR，测试与 CR 不并行。
2. **独立判断**：每个智能体不复用前者的结论，自己验证。
3. **启动安全优先**：触及入口/调度器/配置/依赖清单的改动，提交前必须验证能启动。
4. **主控者兜底**：智能体报告后，主控者亲自核验测试数和编译/import，不能盲信。
5. **只在选定工作区内工作**：三个智能体使用同一路径，不碰其他工作区。
6. **评审与实现分离**：CR 不修源码，修复统一回炉开发智能体；测试智能体仅限修本阶段测出的明显小问题并重跑验证。
7. **提交分层把关**：CR 通过后由 CR 智能体提交并推送本 Phase 成果（分支按与用户确认的选择）；**合并主分支必须用户人工审核 + 线下验证后明确确认**，绝不自动合并。

## 技术栈命令速查（启动安全检查用）

先探测项目根的清单文件确定技术栈，再选命令。多语言项目（如 Rust 后端 + 前端）需对每部分都跑。

| 技术栈 | 探测标志 | 编译/语法检查 | 测试 |
| --- | --- | --- | --- |
| **Rust** | `Cargo.toml` / `Cargo.lock` | `cargo build`（或 `cargo check` 更快） | `cargo test` |
| **Node/TS** | `package.json` / `tsconfig.json` | `npx tsc --noEmit`（TS）；`npm run build`（前端） | `npm test` / `npx vitest` / `npx jest` |
| **Python** | `pyproject.toml` / `requirements.txt` / `setup.py` | `python -m compileall <改动目录> -q` | `python -m pytest` |
| **Python import 检查** | — | `python -c "from <module> import <新符号>"` | — |
| **Go** | `go.mod` | `go build ./...`；`go vet ./...` | `go test ./...` |

> 涉及容器化部署的项目（如 `docker ps` 能看到运行中的开发容器），对应命令需加 `docker exec <容器名>` 前缀在容器内执行；优先使用项目自带脚本（如 `./scripts/dev_test.sh`），不要绕过。
